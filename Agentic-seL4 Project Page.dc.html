Overview

Why sandbox an agent at the kernel?

Agentic AI is being used for optimisation, self-healing and automated decision making in exactly the sectors that depend on strong isolation. But an agent is stochastic and prompt-driven rather than a fixed program. Even during normal operation it may leak sensitive data, misconfigure systems, escalate its own privileges, or introduce subtle vulnerabilities in response to benign instructions. Under attack it amplifies the adversary: following malicious prompts, chaining tools, exfiltrating data across trust boundaries, and weakening defences faster and more persistently than a human operator.

Today's containment is empirical. Linux primitives, containers and VM-based sandboxes all fail through incomplete enforcement, misconfiguration, flawed policies and buggy runtimes — and benchmarks that measure escape are, by construction, post hoc. They cannot deliver machine-checked isolation guarantees.

seL4 can. Its capabilities may be delegated, restricted or revoked, and they are already a formally analysable foundation with machine-checked information-flow proofs. What is missing is a layer above the kernel that is agent-aware — fine-grained, dynamically delegated, and robust against active probing by the agent itself — together with the security theorems that such a layer induces.

Goal one

Provide provably secure sandboxing for systems comprising AI agents, using the capability-enabled seL4 microkernel as the foundation for isolation.

Goal two

Use AI agents to support the new security theorems this extension induces, underpinned by modernisation of the existing seL4 theorems and proofs.

Work packages

Four objectives, two strands

WP3 is a project-long proof strand. WP1, WP2 and WP4 run as sprints, feeding requirements and automation back into it. WP2 carries two parallel implementations — a Linux reference design from sprint 2, with the seL4 implementation expected at sprint 5 — both stress-tested with the Red Team.
